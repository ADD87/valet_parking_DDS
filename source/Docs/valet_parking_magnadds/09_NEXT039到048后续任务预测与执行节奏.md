本文用于记录 NEXT-038 之后的连续任务预测。它不是新的大计划替代品，而是当前状态下的 10 步执行路线，防止后续工作在调试细节里绕圈。

## 固定执行节奏

NEXT-041 之后，执行节奏从“单个 NEXT 小步修订、小步调试”切换为“批量检测、批量修订、统一验证、集中排错”。

新的固定节奏：

```text
先批量静态扫描和契约检查
-> 再批量修订代码/脚本/文档
-> 再统一跑 x86 + m57 编译
-> 再统一跑 x86 smoke 矩阵
-> 再集中排查失败项
-> 再补充必要二次修订
-> 再更新 STATUS.yaml、状态快照和决策记录
-> 再提交并推送 applications Git
```

也就是说，后续不再把 NEXT-042、NEXT-043、NEXT-044、NEXT-045、NEXT-046 拆成五次独立的小循环，而是先合并为 `BATCH-042_046` 做一轮批量硬化。除非编译直接阻塞到无法继续，否则先把本批次范围内的明显不一致点一次性修掉，再用统一验证矩阵收口。

批量硬化仍然保持边界：

```text
不修改 compile/
不修改 thirdparty/
不扩大临时 IDL 字段
不把 replan_reason 诊断文本说成正式 DDS 字段
不把 m57 交叉编译说成板端运行通过
```

## 当前判断

当前最专业的路线仍不是立刻搬完整 `Frame/DependencyInjector`，而是在已接入线程 Provider 骨架后，继续把已经跑通的链路做硬：

```text
SelectedSlot -> ROI_DECIDER -> PATH_PROVIDER -> PATH_PARTITION -> SPEED_OPTIMIZER
ParkingCommand DIRECT_* -> OPEN_SPACE_STRAIGHT_PATH -> SPEED_OPTIMIZER
```

原因很简单：这两条链路已经能 x86 DDS 闭环和 m57 交叉编译。NEXT-040 后，普通链路里的 `OpenSpacePathProvider / OpenSpaceThreadManager` 线程骨架也已进入构建和 smoke。后续应该优先验证线程生命周期、候选复用、输出契约和状态诊断，再判断是否接真正 NLP smoother 或完整 Stage 框架。

## 不能越界的点

- 不能把 `replan_reason` 文本里的 `parking_status` 写成正式 DDS 字段已经存在。
- 不能把 m57 交叉编译写成板端运行通过。
- 不能为了快而修改 `compile/`、`thirdparty/`。
- 不能全量复制外部 `parking_algorithm_standalone` 或 `Repair_...`。
- 不能把调试中的临时输出当作真实车端协议。
